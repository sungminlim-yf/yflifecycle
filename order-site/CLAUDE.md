# 고객용 주문 웹 (프론트엔드)

> **도메인**: 고객이 실제로 보는 주문 사이트의 화면·UX·클라이언트 동작.
> **상위 컨텍스트**: 루트 `../CLAUDE.md` (전체 원칙)
> **관련 폴더**: 진입 토큰 발급/승격은 `../onboarding/`, 주문 제출이 쓰는 데이터는 `../airtable/schema.md`, 제출→저장 흐름은 `../n8n/`

---

## 이 폴더가 다루는 것

- 주문 페이지 설계 (매직 링크 진입 화면 / 게스트 진입 화면)
- 이번 주문만 다른 배송지 UX
- 주문 컷오프 표시
- 매직 링크 분실 대응 (4겹 방어) + 재발급 보안 규칙

> 품목 3종뿐이라 **한 화면에서 주문 완결**하는 매우 단순한 UI가 목표.

---

## 주문 페이지 설계

### 매직 링크 진입 시 (정문 A)

- 상단 강조 배너: "○○○님, △△식당 전용 주문 페이지입니다"
- 가게명, 담당자명, 이메일, 기본 배송지, payment term 표시
- "내 가게 정보가 아닌가요? 담당 영업사원에게 연락해 주세요" 안내

### 글로벌 진입 시 (게스트, 정문 B)

- 상단 배너 없음. 빈 입력 폼 (상호·연락처)
- "이미 등록된 가게이신가요? 전화번호/이메일로 내 전용 페이지 찾기" 안내

### 이번 주문만 다른 배송지

화면에서는 "이번만 다른 곳으로 받기" 토글. 데이터는 Airtable에 3개 필드로 관리(기본/이번주문/실제(수식)) — 상세 `../airtable/schema.md`.

### 주문 컷오프

- **오더 컷오프 = 배송 전날 12pm**. 컷오프가 닫히면 익일(D+1) dispatch 수량 확정.
- 화면에 다음 가능 배송일·마감 시각을 명확히 표시.

## 매직 링크 분실 대응 (4겹 방어)

| 대책 | 작동 시점 | 손이 가는 정도 |
| --- | --- | --- |
| 주문 확인 문자/이메일에 링크 동봉 | 매 주문마다 자동 | 거의 없음 |
| 주문 완료 화면에서 홈 화면 추가 유도 | 주문 직후 | 없음 (PWA, iOS는 안내만 가능) |
| 글로벌 사이트에서 번호/이메일로 링크 받기 | 분실 후 재진입 시 | 없음 (자동 조회·발송) |
| QR 스티커 (2회+ 재요청 고객) | 재요청 누적 시 자동 추천 | 영업 방문 시 부착 |

- **핵심 통찰**: 사장님들은 자기 가게 전화번호를 절대 잊지 않는다 → 전화번호로 링크 재발급

### 재발급 보안 규칙

- 전화번호 **또는** 이메일 중 하나로 조회 가능
- 링크는 **반드시 파일에 등록된 그 연락처로만** 발송 (사용자가 지정한 다른 곳으로 발송 불가)
- 매칭 실패해도 존재 여부 노출 금지 ("등록돼 있다면 발송했습니다" 식 동일 응답)
- **rate limit** 필수 (SMS 폭탄·enumeration 차단)
- QR 트리거: 재요청 2회 이상 → Airtable 자동화로 영업에 Slack 알림 + QR 스티커 추천 플래그

> 토큰 자체의 발급/폐기 정책은 `../onboarding/`. 재요청 카운트 필드는 `../airtable/schema.md`(고객 테이블). 문자 발송·알림 워크플로우는 `../n8n/`.

## 미결 사항 (이 도메인)

| 항목 | 선택지 / 메모 |
| --- | --- |
| 전용 페이지 정보 노출 범위 | 이메일·주소 전체 노출 vs 부분 마스킹 |
| 주문 검토/완료 화면 | 제출 전 확인 단계 유무, 완료 화면 구성 |
| 선결제 시 정보 수정 허용 범위 | 배송지 수정 허용, 가게명 고정 등 |
| QR 재요청 카운트 기준 | 링크 재요청 횟수만 vs 링크 클릭 포함 합산 |
| 문자 발송 서비스 | 호주 기준: Twilio 등 (국내 서비스 불가) |
